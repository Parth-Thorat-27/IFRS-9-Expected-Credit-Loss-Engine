# Performance: row-by-row vs set-based ECL

Generated by `python/benchmark_ecl.py` on 2026-10-13. Every number below was measured in that run; nothing is estimated.

## Set-up

- Month: 2019-03-31, 99,922 loans, 3 scenarios; 3,419,382 loan-scenario-month rows (each loan's horizon: 12 months in Stage 1, the remaining term in Stage 2, none in Stage 3).
- Database: Oracle Database Free 23.26.3.0.0 in Docker (Free is limited to 2 CPU threads).
- Client machine: Windows build 10.0.26200, Python 3.11.9.
- Each variant ran 3 times on an empty target table; the table shows every run and the fastest. Times are `BATCH_RUN.elapsed_seconds`, measured inside the database.

## What the numbers say

- **The spec's comparison (production against the naive version):** run_v2 (production) 7.45 s against run_v1 8.09 s: run_v2 (production) is 1.1x faster than run_v1.
- **Processing style, same arithmetic:** with BINARY_DOUBLE, run_v2 (production) 7.45 s against row by row, BINARY_DOUBLE 4.02 s: row by row, BINARY_DOUBLE is 1.9x faster than run_v2 (production); with NUMBER, set-based, NUMBER 32.48 s against run_v1 8.09 s: run_v1 is 4.0x faster than set-based, NUMBER.
- **Arithmetic, same processing style:** set-based, NUMBER 32.48 s against run_v2 (production) 7.45 s: run_v2 (production) is 4.4x faster than set-based, NUMBER; run_v1 8.09 s against row by row, BINARY_DOUBLE 4.02 s: row by row, BINARY_DOUBLE is 2.0x faster than run_v1.
- **Algorithm:** closed-form sum 1.88 s against run_v2 (production) 7.45 s: closed-form sum is 4.0x faster than run_v2 (production).

## Why

**Arithmetic.** Oracle `NUMBER` is exact decimal arithmetic with up to 38 significant digits, done in software. `BINARY_DOUBLE` is the processor's floating point. The ECL is mostly powers, products and divisions, so the number type decides much of the run time. Floating point is used only for the probability and discount maths: Stage 3 losses and floors stay in exact `NUMBER`, every stored amount is converted back to `NUMBER` and rounded to cents, and `run_v1` stays in exact `NUMBER` on purpose, so `compare_versions` proves on every loan that the floating point never changes a cent.

**Processing style.** A row-by-row loop usually loses because it pays a switch between the PL/SQL and SQL engines for every fetch, function call and single-row INSERT. Inside the database that switch is cheap, and the loop has a structural advantage here: it walks each loan's schedule month by month, building survival, discount factor and balance from the previous month with a multiplication or two. The month-row statement has no previous row to build on (that is what makes it set-based), so every one of the 3,419,382 loan-month rows recomputes its factors from closed forms and travels through the join and the aggregation. With the same arithmetic, that made the loop the faster of the two at this size.

**Algorithm.** The monthly sum is a geometric series, so it has a closed form: `ECL = LGD [k1 (1 - s^H) + h k2 v (1 - (s v)^H) / (1 - s v)]` with s = 1 - h, v = 1/(1 + r), k1 = (B - P/r)/(1 + r), k2 = P/r. That needs one row per loan and scenario instead of one per month, and it was the fastest variant. Production keeps the month rows anyway: each month's loss stays an explicit, auditable term of the methodology formula, and the run is already a few seconds a month. The closed form shows how much headroom there is if the book grows.

Three other ideas made no material difference when measured while building (on the same month, not re-run by this script): computing `(1 + r)^(t-1)` once per row instead of twice, precomputing the per-loan constants so each month row is a short expression, and a `PARALLEL(2)` hint.

## Lesson

Set-based is not automatically faster. Measure, then fix what the time is actually spent on: here the number type and the amount of work per loan mattered more than loop versus single statement.
